Designing RESTful APIs the Right Way

Practical principles I follow when designing clean, consistent, and maintainable REST APIs.

Nov 18, 2025 • 4 min read
REST APINode.jsBackend

An API is a contract. Once a frontend, a mobile app, or another team depends on it, every inconsistency becomes their problem. Over several backend projects I have collected a set of principles that keep my APIs predictable. None of them are new, but applying them consistently makes a big difference.

1. URLs Are Nouns, Methods Are Verbs

Resources should be named with plural nouns, and the HTTP method should describe the action:

GET    /students          → list students
POST   /students          → create a student
GET    /students/:id      → get one student
PATCH  /students/:id      → update part of a student
DELETE /students/:id      → delete a student

Avoid URLs like /getStudents or /createStudent. The method already says what happens. Nested resources express relationships: GET /students/:id/attendance.

When an action does not fit CRUD, such as approving a request, it is fine to model it as a sub-resource: POST /requests/:id/approval.

2. Use Status Codes Honestly

Returning 200 with { "error": "..." } in the body forces every client to parse the body to find out whether the request worked. Status codes exist for this:

  • 200 OK: successful read or update.
  • 201 Created: a new resource was created.
  • 204 No Content: success with nothing to return, often for deletes.
  • 400 Bad Request: the request is malformed or fails validation.
  • 401 Unauthorized: the client is not authenticated.
  • 403 Forbidden: authenticated, but not allowed.
  • 404 Not Found: the resource does not exist.
  • 409 Conflict: the request conflicts with the current state, such as a duplicate email.
  • 500 Internal Server Error: something went wrong on our side.

3. One Error Format Everywhere

Every error should have the same shape, so the client can handle all of them with one piece of code:

{
    "error": {
        "code": "EMAIL_TAKEN",
        "message": "A user with this email already exists",
        "details": []
    }
}

A machine-readable code lets the frontend react to specific cases, while message stays human-readable. Never send stack traces or raw database errors to the client.

4. Paginate, Filter, and Sort with Query Parameters

Collections grow, so list endpoints should be paginated from day one. Query parameters keep the URL structure clean:

GET /students?page=2&limit=20&sort=-createdAt&status=active

Return pagination metadata alongside the data so the client can build navigation without guessing:

{
    "data": [ /* ... */ ],
    "meta": { "page": 2, "limit": 20, "total": 134, "totalPages": 7 }
}

Always enforce a maximum limit on the server. Otherwise a single request for limit=100000 can hurt everyone.

5. Validate Everything at the Boundary

Treat every request as untrusted. Validate the body, params, and query against a schema before any business logic runs, and strip fields the client is not allowed to set. This protects against both bugs and abuse, and it keeps services free of defensive checks.

6. Do Not Leak Internals

  • Expose stable public identifiers instead of internal database IDs where possible.
  • Never return fields like password hashes, even by accident. Explicit response mapping is safer than returning the whole database document.
  • Keep field names consistent. If one endpoint uses createdAt, none should use created_date.

7. Version From the Start

Prefixing routes with a version (/api/v1/...) costs nothing today and makes it possible to introduce breaking changes later without breaking existing clients.

8. Think About Retries

GET, PUT, and DELETE should be idempotent: calling them twice has the same effect as calling them once. POST is not. For operations where a duplicate would be harmful, such as payments or bookings, accept an idempotency key from the client so a retried request does not create a second record.

Summary

Good API design is mostly about consistency. Predictable URLs, honest status codes, one error format, and safe defaults for pagination and validation make an API pleasant to use and easy to maintain. When I review my own endpoints, I ask one question: could a new developer guess how this works without reading the code? If the answer is yes, the design is probably right.
