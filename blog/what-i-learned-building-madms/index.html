What I Learned Building MADMS

Lessons learned while designing and building a modular enterprise backend, including authentication, RBAC, validation, database design, and business modules.

Nov 12, 2025 • 4 min read
MADMSNode.jsMongoDB

MADMS is a modular enterprise management system I built on Node.js, Express, and MongoDB. It covers student management, attendance, complaint handling, phone requests, and shared master data, all protected by role-based access control. The case study describes what the system does. This article is about what building it taught me.

1. Organize by Feature, Not by File Type

My earlier projects had the classic layout: one controllers/ folder, one models/ folder, one routes/ folder. With five modules, each of those folders filled up with unrelated files, and working on a single feature meant jumping across the whole tree.

In MADMS, each business module owns its own folder:

src/modules/
├── students/
│   ├── student.routes.js
│   ├── student.controller.js
│   ├── student.service.js
│   ├── student.repository.js
│   ├── student.model.js
│   └── student.validation.js
├── attendance/
├── complaints/
├── phone-requests/
└── master-data/

Everything about students lives together. Adding a new module means adding a new folder, and deleting one is just as clean. This single decision made the project far easier to navigate.

2. Layers Only Help If You Respect Them

The system follows Router → Controller → Service → Repository → Model. The value of that structure comes from discipline: controllers never query the database, services never touch req or res, and repositories never contain business rules.

The first time I was tempted to "just add a quick query" inside a controller, I realized that every shortcut like that would erode the structure. Keeping the boundaries strict meant I could later change how data was fetched without touching a single business rule.

3. Validate at the Edge

Every request body is validated with Joi before it reaches the controller. A small reusable middleware keeps it tidy:

const validate = (schema) => (req, res, next) => {
    const { error, value } = schema.validate(req.body, { abortEarly: false, stripUnknown: true });
    if (error) {
        return next(new ValidationError(error.details.map(d => d.message)));
    }
    req.body = value;
    next();
};

stripUnknown turned out to be important: it silently drops fields the client should not be setting, such as role or deletedAt, which closes a whole class of mass-assignment bugs.

4. Design RBAC Before You Need It

I planned roles and permissions at the start rather than retrofitting them. Each route declares the permission it needs (for example complaints:resolve), and roles are just collections of those permissions. When new roles were needed later, they were configuration changes, not code changes. I wrote more about this approach in Understanding RBAC in Enterprise Applications.

5. Soft Delete and Public IDs Belong in the First Schema

Two database decisions saved me from painful refactors:

  • Soft delete. Records get a deletedAt timestamp instead of being removed. Attendance history and complaint records stay intact for auditing, and an accidental delete can be undone.
  • Public identifiers. The API exposes a separate publicId instead of MongoDB's internal _id. Internal IDs never leak, and the database could change without breaking any client URLs.

Both are easy to add on day one and very hard to add once data and clients already exist.

6. One Error Handler, One Response Shape

Early on, different endpoints returned errors in different shapes. The frontend had to guess. I replaced all of that with custom error classes and a single error-handling middleware, so every error looks the same:

{
    "success": false,
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "Invalid request data",
        "details": ["\"phone\" must be a valid number"]
    }
}

Successful responses follow a matching envelope. Consistency like this is invisible when it works and painful when it is missing.

7. Lists Need Pagination From the Start

A list endpoint that returns everything works fine with fifty test records and breaks with real data. Every list in MADMS supports page, limit, sorting, and filtering, implemented once in a shared helper and reused by each repository.

What I Would Do Differently

  • Write tests earlier. The layered structure made services easy to test, but I added tests later than I should have. Testing business rules as they are written is much cheaper.
  • Document the API as I go. An OpenAPI spec maintained alongside the routes would have made frontend integration smoother.
  • Consider TypeScript. As the number of modules grew, types would have caught a number of small mistakes before runtime.

Final Thoughts

The biggest lesson from MADMS is that structure is a feature. None of these decisions are complicated on their own, but together they made a growing system feel predictable. When I open any module, I know exactly where everything is, and that is what makes a codebase maintainable.
