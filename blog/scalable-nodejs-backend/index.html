Building a Scalable Node.js Backend

How I structure a scalable Node.js backend using separation of concerns, modular architecture, controllers, services, repositories, and models.

Oct 15, 2025 • 5 min read
Node.jsExpressArchitectureBackend

When I first started learning Node.js and Express, my approach was simple: put everything inside the route handler. It worked perfectly for small projects and tutorials. But as I started building more complex applications, I quickly realized that this approach leads to messy, unreadable, and hard-to-test code—often called "Spaghetti Code."

In this post, I want to share my journey of moving from a basic Express setup to a structured, scalable modular architecture. This is a crucial step for any junior developer looking to build production-ready backend systems.

The Problem: Fat Controllers

Here is what my early code looked like. Everything—from parsing the request, validating data, checking the database, hashing passwords, and sending the response—was stuffed into one massive function.


// The "Bad" Way: Doing everything in the route handler
app.post('/api/users/register', async (req, res) => {
    try {
        // 1. Validation
        if (!req.body.email || !req.body.password) {
            return res.status(400).json({ error: 'Missing fields' });
        }
        
        // 2. Database check
        const existingUser = await User.findOne({ email: req.body.email });
        if (existingUser) {
            return res.status(400).json({ error: 'Email already in use' });
        }
        
        // 3. Business logic (hashing password)
        const salt = await bcrypt.genSalt(10);
        const hashedPassword = await bcrypt.hash(req.body.password, salt);
        
        // 4. Database save
        const newUser = new User({
            email: req.body.email,
            password: hashedPassword
        });
        await newUser.save();
        
        // 5. Send response
        res.status(201).json({ message: 'User created' });
    } catch (error) {
        res.status(500).json({ error: 'Server error' });
    }
});

This works, but imagine having 50 routes like this! It becomes impossible to maintain or test the business logic without mocking the entire HTTP request.

The Solution: Separation of Concerns

To solve this, I learned about a 3-layer architecture often used in Node.js applications: Controllers, Services, and Repositories (or Models).

  • Controllers: Their only job is to handle HTTP requests. They receive the request, pass data to the service, and send back the HTTP response.
  • Services: This is where the core business logic lives. They don't know anything about HTTP (req, res).
  • Models/Repositories: They handle direct communication with the database.

The Refactored Code

Here is how that same registration logic looks when properly separated:

1. The Service Layer (user.service.js)


const User = require('../models/User');
const bcrypt = require('bcrypt');

class UserService {
    async registerUser(email, password) {
        const existingUser = await User.findOne({ email });
        if (existingUser) {
            throw new Error('Email already in use');
        }

        const salt = await bcrypt.genSalt(10);
        const hashedPassword = await bcrypt.hash(password, salt);

        const newUser = new User({ email, password: hashedPassword });
        return await newUser.save();
    }
}

module.exports = new UserService();

2. The Controller Layer (user.controller.js)


const UserService = require('../services/user.service');

class UserController {
    async register(req, res, next) {
        try {
            const { email, password } = req.body;
            
            if (!email || !password) {
                return res.status(400).json({ error: 'Missing fields' });
            }

            // Call the service (Controller doesn't care HOW the user is created)
            const newUser = await UserService.registerUser(email, password);
            
            res.status(201).json({ message: 'User created', userId: newUser._id });
        } catch (error) {
            // Pass to global error handler
            next(error);
        }
    }
}

module.exports = new UserController();

3. The Router (user.routes.js)


const express = require('express');
const UserController = require('../controllers/user.controller');
const router = express.Router();

router.post('/register', UserController.register);

module.exports = router;

Why this matters for Junior Developers

Taking the time to structure my projects this way felt like extra work at first. But the benefits were immediate:

  1. Easier to Read: When I look at a route, I immediately know what it does.
  2. Reusable Code: If I need to create a user from an Admin dashboard or a CLI script, I can just call UserService.registerUser() without faking an HTTP request.
  3. Better Testing: I can write unit tests for my Service layer easily because it's just plain JavaScript functions returning data.

Learning this architecture was a huge turning point for me. It bridged the gap between writing code that just works, and writing code that is professional and maintainable.
