Backend Engineering

From CRUD APIs to Business Logic

Why real-world enterprise applications require more than basic CRUD operations, and how business rules can be organized into reliable backend services and engines.

Nov 05, 2025 • 4 min read
REST APIBusiness LogicBackend

Most backend tutorials teach CRUD: create, read, update, delete. It is the right place to start, and for a to-do app it is the whole story. But when I started working on systems that model real operations, such as warehouses, meal planning, and request workflows, I found that CRUD was only the surface. The real value of the backend was in the business rules that decide what is allowed to happen and what must happen next.

Where CRUD Stops Being Enough

Consider a warehouse. A naive API might expose PATCH /items/:id and let the client set the new quantity. That is technically CRUD, but it ignores every question the business actually cares about:

  • Which batch should the stock come from?
  • What happens if there is not enough stock?
  • Is any batch about to expire?
  • Does this withdrawal push the item below its reorder level?
  • Who requested it, and can we trace it later?

If the client simply sends a new number, all of those rules either live in the frontend (where they can be bypassed) or nowhere at all.

Model Actions, Not Just Records

The shift that helped me most was designing endpoints around business actions instead of raw updates:

POST /stock/receipts      → receive a new batch
POST /stock/issues        → issue stock to the kitchen
POST /stock/adjustments   → record a counted difference, with a reason

Each action has its own validation, its own rules, and its own audit trail. The quantity on hand is never edited directly; it is the result of these movements.

Example: Issuing Stock with FEFO

In the military mess and warehouse system, perishable items are issued using FEFO (First Expired, First Out): the batch that expires soonest is consumed first. Here is a simplified version of that rule as a service:

async function issueStock({ itemId, quantity, requestedBy }) {
    const batches = await batchRepository.findAvailable(itemId, { sortBy: 'expiryDate' });

    const available = batches.reduce((sum, b) => sum + b.remaining, 0);
    if (available < quantity) {
        throw new BusinessRuleError(`Only ${available} units available`);
    }

    let remaining = quantity;
    const allocations = [];
    for (const batch of batches) {
        if (remaining === 0) break;
        const take = Math.min(batch.remaining, remaining);
        allocations.push({ batchId: batch.id, quantity: take });
        remaining -= take;
    }

    await movementRepository.recordIssue({ itemId, allocations, requestedBy });
    await reorderService.checkLevel(itemId);
    return allocations;
}

The controller that calls this function does not know anything about batches or expiry dates. It just passes the request along and returns the result. All of the decisions live in one testable place.

Two Kinds of Validation

It helps to separate validation into two layers:

  1. Shape validation checks that the request is well-formed: quantity is a positive number, itemId is present. A schema library like Joi handles this at the edge, before the service runs.
  2. Business validation checks that the request makes sense in the current state of the system: there is enough stock, the item is not blocked, the user's department may request it. This needs the database, so it belongs in the service.

Mixing the two makes both harder to read. Keeping them apart makes it obvious where a new rule should go.

State Machines for Workflows

Many business objects move through a lifecycle. A complaint, for example, might go from Open to In Review to Resolved or Rejected. If any status can be set from any other, the data quickly becomes inconsistent. A small transition map prevents that:

const transitions = {
    open:      ['in_review', 'rejected'],
    in_review: ['resolved', 'rejected'],
    resolved:  [],
    rejected:  [],
};

function assertTransition(from, to) {
    if (!transitions[from].includes(to)) {
        throw new BusinessRuleError(`Cannot move from ${from} to ${to}`);
    }
}

It is a few lines of code, but it turns an implicit agreement into an enforced rule.

Errors That Speak the Business Language

When a rule is violated, the client should get a clear, specific message, not a generic 500. I use small custom error classes such as BusinessRuleError, NotFoundError, and ForbiddenError, and a central error handler maps them to the correct HTTP status (409, 404, 403). The service throws; the handler formats. Neither needs to know about the other.

Consistency Matters

Business operations often touch several records at once: decrementing batches, recording a movement, and maybe creating a reorder alert. If one of those writes fails halfway, the data is wrong. Wrapping related writes in a database transaction ensures they succeed or fail together.

Key Takeaways

  • Design endpoints around what the business does, not just around the tables.
  • Keep business rules in services, where they are reusable and testable.
  • Separate request-shape validation from business-rule validation.
  • Make lifecycles explicit with simple state machines.
  • Use transactions when one action changes several records.

CRUD gets data into the system. Business logic is what makes the system trustworthy. Learning to see that difference changed how I approach every backend I build.
