DevOps & SRE

From Full Stack Development to DevOps and SRE

Why I am expanding beyond application development into cloud infrastructure, DevOps, reliability engineering, automation, and scalable systems.

Dec 22, 2025 • 4 min read
DevOpsSRECloudAWS

For most of my journey so far, "done" meant the feature worked on my machine and the pull request was merged. But software does not deliver value in a repository. It delivers value while it is running, serving real users, at three in the morning, under load. That realization is why I am expanding beyond application development into DevOps and Site Reliability Engineering (SRE).

The Gap I Kept Noticing

While building backends, I kept running into questions my code could not answer on its own:

  • How does this application get from Git to a server, reliably, every time?
  • How would I know it is slow or failing before a user reports it?
  • What happens when traffic doubles, or when a dependency goes down?
  • How do I roll back a bad release in minutes instead of hours?

These are DevOps and SRE questions, and I realized that a developer who understands them builds better software from the start.

DevOps vs SRE

The two are closely related but have different emphasis:

  • DevOps is a culture and set of practices that removes the wall between building software and running it: automation, CI/CD, infrastructure as code, and shared ownership.
  • SRE, which originated at Google, is a concrete way to implement that culture by treating operations as a software engineering problem, with reliability measured and managed using data.

SRE Concepts That Changed My Thinking

SLIs, SLOs, and Error Budgets

An SLI (Service Level Indicator) is something you measure, such as the percentage of requests that succeed or the latency of the slowest 1%. An SLO (Service Level Objective) is the target for it, for example "99.9% of requests succeed over 30 days".

The interesting part is the error budget: a 99.9% target allows about 43 minutes of failure per 30-day month. If the service stays within budget, the team can ship faster and take more risks. If the budget is spent, the focus shifts to reliability. It turns "move fast" versus "be stable" from an argument into a number.

Toil

SRE defines toil as manual, repetitive work that scales with the size of the service and adds no lasting value. Manually deploying, restarting services, or copying logs are all toil. The goal is to engineer it away with automation, which is very appealing to me as a developer.

Observability

Logs, metrics, and traces let you ask questions about a running system. Structured logs with request IDs, metrics dashboards in tools like Prometheus and Grafana, and alerts based on SLOs (not on every CPU spike) make the difference between guessing and knowing.

The Skills I Am Building

Containers

Docker packages an application with everything it needs, so it runs the same way everywhere. A simple Node.js image looks like this:

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
EXPOSE 3000
CMD ["node", "src/server.js"]

CI/CD

Every push should be tested automatically, and every merge to the main branch should be deployable. A minimal GitHub Actions pipeline:

name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test

Infrastructure as Code

Tools like Terraform describe servers, networks, and databases in version-controlled files. Infrastructure becomes reviewable, repeatable, and recoverable, just like application code.

Cloud and Orchestration

AWS fundamentals (which I cover in Preparing for AWS Cloud Practitioner) and Kubernetes for running containers at scale complete the picture.

Why a Full-Stack Background Helps

I do not see this as leaving development behind. Knowing how applications are built is a real advantage in operations:

  • I understand what the application needs: environment configuration, health checks, graceful shutdown, and database migrations.
  • I can read the code when an incident happens, instead of treating it as a black box.
  • I can build observability into the application itself, not bolt it on afterwards.

And the reverse is true too: thinking like an SRE makes me write better backend code, with timeouts, retries, clear logs, and fewer hidden single points of failure.

My Plan

  1. Containerize my existing projects and run them with Docker Compose.
  2. Add CI pipelines with automated tests to every repository.
  3. Deploy a project to AWS using infrastructure as code.
  4. Add monitoring, dashboards, and SLO-based alerts to a running service.
  5. Continue with deeper AWS certifications and Kubernetes.

Conclusion

Writing code is only half of software engineering. The other half is making sure that code runs reliably for the people who depend on it. Moving toward DevOps and SRE is my way of owning the whole lifecycle, from the first commit to the system running smoothly in production.
